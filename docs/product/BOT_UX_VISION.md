# Job Inside — идеальный UX бота

Тема часа: H1. Опора: patch-15 + research 2026-08-24.  
Принцип: продукт, который хочется открыть снова = ясные статусы, честные сроки, выход с каждого шага, без вранья в цифрах.

## 10 секунд на понимание

После `/start` человек должен ответить себе на один вопрос: **«мне платят за локальную работу»** или **«я заказчик, мне нужен процесс»**. Сейчас welcome — простыня + сразу 5 кнопок меню. Это меню исполнителя, заказчик теряется.

Целевое первое сообщение (черновик, тон — `COPY_SYSTEM.md`):

> Job Inside — сервис локальных заданий на картах.  
> Исполнитель: понятные задания, проверка, баланс, вывод.  
> Бизнес: бриф и онбординг через менеджера.  
> Кто вы?

Кнопки (2–3, не 5): `Хочу задания` · `Я представляю бизнес` · `Правила`

## Северная звезда экранов

1. **Один следующий шаг.** Не «вот меню из всего».
2. **Статус всегда назван по-человечески** + что делать дальше.
3. **Выход** с каждого inline-экрана (уже почти есть `to_menu` — держать везде).
4. **Тишина запрещена.** Сдал скрин → «принято, проверка обычно до N часов» (N = ASSUMPTION, факт из очереди модерации).
5. **Деньги отдельно от задания.** Реквизиты в кабинете (уже так в patch-15) — не спрашивать на каждом скрине.
6. **Честно про правила площадок.** Не учим обходить ToS. Учим: свой город, своя практика, качественный текст, скрин как доказательство работы.

## Первый /start

### Сейчас (patch-15)

1. Rules middleware — длинный текст: «мы платим ВАМ», рефералка, канал, **промо прокси с захардкоженным URL**.
2. Кнопка «Принять правила» + ссылка на прокси.
3. Welcome из `BotSetting` + reply-меню исполнителя.
4. Реферал пишется только если пользователь **создан в этом апдейте**.

### Почему слабо

- Нет сегментации (Telega/BotHero: 30–60 сек на intent).
- Правила ≠ правила: это лендинг+оффер+партнёрка.
- Прокси в онбординге бьёт по доверию и тащит секрет в git.
- Повторный `/start` не говорит «ты уже внутри, вот статус».

### Цель

| Шаг | Сообщение | Кнопки | Событие |
|---|---|---|---|
| 1 | Кто вы + одно предложение что это | Исполнитель / Бизнес / Правила | `start` `{role_intent}` |
| 2a Исполнитель | Коротко: город ближе к вам, скрины, проверка, вывод от min ₽ | К заданиям / Кабинет | `onboarding_done` `{path:executor}` |
| 2b Бизнес | «Сайта ещё нет. Напишите менеджеру — разберём точку и площадки» + SUPPORT | Написать / Стать исполнителем | `onboarding_done` `{path:biz}` |
| 3 Правила | 5–7 буллетов: качество, свой опыт, запрет накрутки, модерация, вывод | Принять | `rules_accept` |

Gate канала: либо честный «подпишитесь, нам так удобнее сообщать слоты» **без** претензии на проверку, либо реальный `getChatMember`. Сейчас — самоклик (`news_accepted`).

## Доверие

Доверие в гиг-боте = предсказуемые деньги и понятный отказ.

Минимум на карточке задания (сейчас нет инструкции до «Начать»):

- Площадка, город организации, сфера, цена — уже есть
- **Добавить:** дедлайн сдачи (если есть), что считается доказательством, «проверка обычно X ч» 
- Ссылка/инструкция — сразу или по кнопке «Открыть инструкцию», не прятать за стартом попытки

Кабинет должен отвечать на 3 страха:

1. Сколько у меня сейчас (баланс) — есть
2. Где моя последняя сдача (статус) — история отзывов есть, но без очереди «ждёт проверки N часов»
3. Когда выплата (заявка на вывод: принято / в работе / выплачено) — **нет статусного экрана заявки**

Research (gruv.ai / TechVinta): видимый SLA и причина отказа снижают отток после fail сильнее, чем «вежливый отказ без деталей».

## Статусы задания — целевой словарь

| Код (есть в Attempt) | Текст исполнителю | Что дальше |
|---|---|---|
| `waiting_approval` | Проверяем профиль по этому заданию | Ждите. Обычно до X ч. ASSUMPTION: снять медиану из `admin_analytics` |
| `login_screenshot` | Ждём скрин входа/аккаунта | Пришлите фото. Кнопка отмены есть |
| `approved` | Профиль ок. Можете публиковать отзыв по инструкции | Скрин готового отзыва |
| `review_submitted` | Отзыв на проверке | Не дублируйте скрин. Напомним, когда можно следующее |
| `completed` | Принято. +N ₽ на баланс | Кабинет / вывод / следующее |
| `rejected` | Не приняли. Причина: … | Что исправить **или** взять другое. Без «вы мошенник» |
| `declined` | Профиль по заданию не подтвердили. Причина: … | Другое задание / уточнить в поддержке |
| `canceled` | Отменили | Меню |

Пустое: «Сейчас нет заданий в вашем городе» + «напомнить, когда появятся» (сейчас: «Сейчас нет активных заданий» — тупик).

## Кабинет

Оставить: ID, баланс, выполнено, реквизиты, история отзывов, история операций.

Добавить:

- Последняя активная попытка (1 карточка сверху)
- Заявки на вывод: сумма / статус / дата
- Если реквизиты пустые — не прятать в подменю, CTA «чтобы вывести, укажите реквизиты»

Ошибка «реквизиты < 4 символов» при сдаче отзыва — правильный гейт, плохой момент. Просить реквизиты **после первого completed** или при первом «Начать», не в момент скрина.

## Вывод

Сейчас: сумма → реквизиты → заявка. Меню перехватывает FSM (хорошо).

Не хватает:

- Подтверждение «списать N ₽, уйдут на …, обычно до D дней» (D = ASSUMPTION, факт из `WithdrawalRequest` paid-at − created-at)
- Статус «заявка #id в работе»
- Повторная заявка, пока pending — запретить явно текстом

Успех выплаты: не только «💰 Выплата выполнена», а сумма, способ, «можно брать следующее».

## Рефералка

Механика ясная (ссылка, 20/5). Слабое:

- Стена капса и «пассивный доход» — звучит как гифт-схема. Тон: «процент с принятых заданий приглашённых, не с регистрации».
- Показать: сколько пригласил / сколько из них сделали 1 completed (иначе люди спамят ссылкой в пустоту).
- Не обещать доход без оговорки «если задание принято и начислен баланс».

## Пустые состояния и ошибки «по-человечески»

| Ситуация | Сейчас | Цель |
|---|---|---|
| Нет заданий | «Сейчас нет активных заданий.» | Город + «напишем, когда появится слот» |
| Кулдаун/всё пройдено | Кнопка «второй аккаунт» | Честно: один слот на карточку; второй аккаунт — отдельная модерация, не обход |
| Ждём фото, пришёл текст | «не то» generic | «Нужен скрин картинкой. Документ jpg/png тоже ок» (patch-15 уже принимает document — сказать об этом) |
| Задание уже обработано | сухо | «Это задание уже закрыто. Откройте кабинет или возьмите новое» |
| Вывод < минимума | зависит от хендлера | «Минимум N ₽. Сейчас M ₽. Не хватает …» |
| Блок | BLOCKED_TEXT | Коротко + поддержка, без морали |
| Непонятный ввод в меню | часто тишина | Повторить меню + «нажмите кнопку» |

## Что сделать продуктом, который открывают повторно

Не геймификация. **Ритм:**

1. Напоминание «можно снова» уже есть (scheduler) — оставить, лимит 1/платформу, тихие часы (ASSUMPTION 09–21 локально).
2. После completed — одна кнопка «Ещё в этом городе», не полный wizard с нуля.
3. После reject — конкретный фикс, не общее «попробуйте снова».
4. Broadcast ≤ 1–2/день и только с пользой (новые слоты в городе), иначе block-rate (BotHero).

## Не делать

- Схемы обхода ToS карт, «как пройти алгоритм», массовые аккаунты как продукт.
- Фейковые «уже 10 000 выплат» без данных.
- Онбординг из 4 обучающих простынь (master) — patch-15 правильно ушёл в меню; не возвращать.

## Инкремент H1 круг 2 (2026-08-24 ~07:51) — UX-03: ожидание без вранья

Не переписывать блоки выше. Ниже — spec-ready для дневного PR текстов (C-04). Код бота ночью не трогаем.

Опора: `origin/patch-15` `a768bf3` + inbox H8 + research (фейковый прогресс ломает доверие; маркетплейс: статус ≠ тикет в поддержку).

### Почему «Ожидайте» — дыра, а не мелочь

После скрина человек решает, открыть бота снова или забыть. Сейчас все ветки говорят одно и то же: ждите. Нет якоря (id), нет стадии, нет честной уверенности.

Тишина хуже медленной проверки: Unicorn Club — человек не знает, ждать или писать в поддержку. LOW/CODE: двусмысленный статус заказа = главный источник тикетов «что с моим заказом».

### Хаб врёт → исполнителю нельзя обещать очередь админа

Факт H8: `moderation_hub_counts.admission` = только `waiting_approval`. Живая очередь допуска ещё `login_screenshot`. Сорт `id DESC` — новые сверху, stale внизу. Q5 (completed ∧ ¬credited) в хабе нет.

Значит **запрещено** в copy:

| Запрет | Почему врёт |
|---|---|
| «Вы N-й в очереди» / «перед вами M человек» | Цифра хаба ≠ очередь. login_screenshot не в admission |
| «Модератор уже смотрит» | Админ может не видеть карточку в хабе |
| «Проверка 5 / 15 минут» | Медианы `t_mod` в проде нет. Фейковый countdown = ожидание, которое ломается (Frontend Casebook: число = обещание) |
| «Принят и оплачен» на этом шаге | Денег ещё нет. Даже после pass менеджерский слот ждёт `mgr_outpay` |
| Прогресс-бар / «осталось 80%» | Нет реальных событий прогресса, только ручная приёмка |

Честная уверенность сегодня: **грубый диапазон**, не точное время. Фраза-пол: «обычно в рабочие часы». Часы на циферблате — **ASSUMPTION**, пока владелец не запишет их в `BotSetting` (в коде слота нет). Не выдумывать «10:00–19:00 МСК» как факт.

После ≥20 закрытых Q2 (`submitted_at` → решение) — SQL `t_mod` в FUNNELS. Только тогда можно усилить до «обычно в тот же рабочий день», если p50 это держит. Не раньше.

### Шесть полей сообщения (не таймер)

Каждое ожидание отвечает на 6 вопросов. Нет данных — не выдумывать поле, пропустить.

| Поле | Что сказать | Откуда факт |
|---|---|---|
| 1. Стадия | Именованный шаг Attempt, не «обработка» | `waiting_approval` / `login_screenshot` / `review_submitted` / secacc |
| 2. Свежесть | «Скрин получил» = только что. Повторный заход в кабинет — тот же статус, без «обновлено 3 мин назад» (ts в UI нет) | `submitted_at` / `created_at` есть в БД, в кабинете не показываем — не обещать freshness |
| 3. Кто смотрит | «Проверяет человек», не «система» | Ручные очереди admin/manager |
| 4. Уверенность | Грубо: рабочие часы. Не минуты | S2/S3 inbox, не маркетинг |
| 5. Следующий ход | Ничего не слать повторно. Решение придёт сюда | Дубли скрина сейчас молча/«уже отправлен» |
| 6. Fallback | После **следующего рабочего дня** без ответа — поддержка. Не «пишите через 5 мин» | SLA 24ч Q2 / 48ч Q1 = гипотезы; не обещать час ответа саппорта |

### Карта ждать-состояний → текст

S2 = отзыв (inbox Q2, гипотеза 24ч). S3 = допуск (Q1, гипотеза 48ч). Исполнителю **не** писать «24 часа» / «48 часов», пока нет медианы: это внутренний ритм ops, не публичный SLA. Публично — стадия + рабочие часы.

| Когда | Код сейчас (смысл) | Стадия человеку | Severity ops | Текст-цель |
|---|---|---|---|---|
| Скрин профиля / логина | «Скриншот отправлен на модерацию. Ожидайте решение.» | Проверяем профиль по заданию #{id} | S3 (Q1) | id + «обычно в рабочие часы» + не дублировать кадр |
| Скрин отзыва | «✅ Скриншот получен. Ожидайте проверки.» | Работа на проверке, заявка #{id} | S2 (Q2) | то же; **не** «оплачен» |
| Повтор того же отзыва | «уже отправлен / скрин уже принят» | Та же заявка #{id} всё ещё на проверке | S2 | id + «новый кадр не ускорит» |
| Второй аккаунт | «аккаунт на проверке у модератора» | Отдельная проверка аккаунта, не слот | Q3 | без цены задания; рабочие часы |
| Кабинет, статус | `⏸ Отзыв на проверке`; сырой `Статус: {st}` для допуска | Те же человеческие имена, что в ЛС | — | id в истории; completed без credited → «принят, ждём зачисление» (C-16), не UX-03 |
| WD создан | «Ожидайте выплаты» | Не модерация | S1/S4 | UX-05: заявка ≠ перевод. Здесь не смешивать |

Шаблон (подставить стадию и id; часы не выдумывать):

```
Заявка #{id}: {стадия}.
Скрин получил. Смотрит человек, обычно в рабочие часы.
Напишу сюда, как решим. Тот же кадр второй раз слать не нужно.
```

`{стадия}` ∈ «проверяем профиль» | «проверяем работу» | «проверяем второй аккаунт».

Ожидание **до** take (карточка, UX-02): одна короткая строка «проверка вручную, обычно в рабочие часы» — чтобы ожидание не было засадой после скрина (предупредить до обязательства, не после).

### Рабочие часы — кто задаёт

| Слой | Что | Статус |
|---|---|---|
| Публичный copy | «обычно в рабочие часы» | Делать в C-04 сейчас |
| Ops inbox | S2 24ч / S3 48ч | Гипотеза; разбор aged ASC |
| Циферблат в боте | Напр. будни HH–HH TZ | **Нет в BotSetting.** ASSUMPTION: владелец выбирает, потом settings. Не хардкодить в copy ночью |
| Медиана | `t_mod` по 20 Q2 | Снять SQL FUNNELS, когда будет прод |

Не подставлять ops-гипотезу 24ч в ЛС исполнителю: если inbox в красной зоне, обещание «сутки» станет враньём в тот же день.

### Не делать в UX-03

- Автозакрытие сдачи по таймауту «как Fiverr 3 дня» — у нас нет авто-complete Attempt; молчание ≠ pass.
- Countdown на карточке модератора «осталось 4:59».
- Публичный «видимый таймер обеим сторонам» (TechVinta) — только после честной медианы и inbox, который не врёт. Сейчас таймер обеим = двойное враньё.
- Код ночью. Дневной PR: 3–4 `message.answer` + `_review_status_line` + дубли.

Definition of done UX-03: после каждого скрина есть **id + именованная стадия + рабочие часы + «не дублировать»**; ни минуты, ни позиции в очереди, ни «оплачен».
